# Observe Insurance – AI Claims Support Assistant

A voice AI agent ("Ava") that answers inbound calls from customers checking on an insurance claim. It verifies the caller, reads back claim status, answers FAQs, handles escalation and emergencies, and writes a post-call record to an external system.

Built for the Observe.AI AI Agent Engineer take-home assessment.

## Architecture

```
Caller ⇄ Vapi (speech-to-text → LLM → text-to-speech)
              │ tool calls (HTTPS POST)
              ▼
        n8n webhooks ──► Google Sheets
         /lookup-customer   Customers                (Integration 1: read)
         /verify-claim      Customers + Claims       (Integration 1: read)
         /end-of-call       CallLogs (append)        (Integration 2: write)

Knowledge base: Vapi query tool `faq_lookup` over data/faq.md
```

| Layer | Choice | Why |
|---|---|---|
| Voice platform | Vapi | Telephony, STT, LLM, TTS and tool calling in one place |
| LLM | OpenAI gpt-4o-mini | Low latency, which matters on a phone call |
| Backend | n8n Cloud webhooks | Visual, quick to build, easy to explain |
| External system | Google Sheets (private, OAuth) | Readable live during a demo |

## How it is built

**Agent.** One Vapi assistant. The system prompt is in [agent/system_prompt.md](agent/system_prompt.md), and the assistant, tool and analysis settings are in [agent/vapi_config.md](agent/vapi_config.md).

**Call flow.**
1. Greet, ask what the caller needs.
2. Collect the phone number in three parts (area code, next three, last four), repeat each back, then read the full number back for confirmation.
3. `lookup_customer` → `found` and first name only.
4. Ask for the ZIP on the policy → `verify_and_get_claim` → claim details only if the ZIP matches.
5. Read the claim status in plain language. If documents are required, say which ones and how to submit them.
6. Anything else? Then `end_call`.

FAQ questions (hours, address, new claim, claims process) go to `faq_lookup` at any point, with no verification needed.

**Tools.**

| Tool | Type | Returns |
|---|---|---|
| `lookup_customer` | Function → n8n `/lookup-customer` | `{found, first_name}` or `{error}` |
| `verify_and_get_claim` | Function → n8n `/verify-claim` | `{verified:false}`, or `{verified:true, full_name, has_claim, claim_id, claim_type, status, last_updated, docs_required, docs_needed_description, adjuster_note}` |
| `faq_lookup` | Query tool over `data/faq.md` | FAQ passages |
| `end_call` | End call | – |
| `transfer_to_representative` | Transfer / function | See "Known limitations" |

**State.** The conversation itself holds the state (confirmed phone, verified yes/no, attempt counts). The security boundary is in the backend: `lookup_customer` never returns claim data, and `verify_and_get_claim` returns it only when the ZIP matches. A wrong ZIP and an unknown phone return the same `{verified:false}`, so the endpoint cannot be used to find out which numbers are customers.

**Error handling.**
- Google Sheets failure → the workflow returns `{error:true}`; the agent apologizes and offers a representative instead of guessing.
- Phone matching uses the last 10 digits, so formats like `(555) 010-0001` and `+15550100001` both work.
- The post-call record is written from Vapi's end-of-call webhook, not by the agent, so it is logged even if the caller hangs up abruptly. Missing fields fall back to `Unknown`, `neutral` and `info_only`.

## Integrations

**Integration 1: read customer and claim data.** Vapi calls an n8n webhook. n8n reads the `Customers` and `Claims` tabs with the Google Sheets node, matches on phone number, checks the ZIP, and returns JSON in the format Vapi expects (`{results:[{toolCallId, result}]}`).

**Integration 2: write the post-call record.** Vapi extracts a structured output `call_record` (caller name, phone, sentiment, outcome, summary) after the call and posts an `end-of-call-report` to n8n `/end-of-call`. n8n appends one row to `CallLogs`.

| CallLogs column | Source |
|---|---|
| timestamp | Call start time (ISO 8601) |
| caller_name | Full name confirmed after verification, else `Unknown` |
| phone | Number the caller gave |
| summary | Generated by the structured output |
| sentiment | positive / neutral / negative |
| outcome | resolved / escalated / auth_failed / not_found / emergency / info_only |

**Authentication.** n8n connects to Google with OAuth under the owner's account; the sheet is private. Vapi calls n8n over HTTPS webhook URLs.

## Scenarios and how they are handled

| Scenario | How the agent handles it | Logged outcome |
|---|---|---|
| Happy path | Verified by full name, claim status read out | resolved |
| Documents required | Lists the needed documents; portal upload, email, or mail | resolved |
| Authentication failure | Wrong ZIP: one retry, then refuses, shares nothing, offers a representative | auth_failed |
| Customer not found | One retry on the number, then offers help | not_found |
| No claim on file | Verified; says no claim is on file and how to start one | resolved |
| FAQ | Answers from `faq_lookup` | info_only |
| Emergency | Tells the caller to hang up and call 911, stops, ends the call | emergency |
| Unsupported question (coverage, legal, payout) | Declines to guess and offers a representative | varies |
| Representative request | Acknowledges without arguing and escalates | escalated |

## Known limitations

- **Representative handoff.** A live phone transfer needs a real call leg plus a Vapi or Twilio number with outbound calling enabled; it does not work from a browser test call on a trial account. `n8n/workflow_escalate.json` is a mock handoff webhook (the agent calls it, then promises a callback). In production this would be a warm transfer over SIP/Twilio or a callback ticket in a CRM.
- **Webhooks are not authenticated yet.** Production would add a shared-secret header that n8n checks.
- **Attempt limits** (two ZIP tries, two number tries) are enforced by the prompt, not by server-side counters.
- **Speech recognition on digit strings** is imperfect; chunked collection and read-back confirmation reduce the errors.
